# 유지보수 역설 — 잠금 영역을 사람이 직접 고치는 법

이 레포는 기획자가 Claude Code 로 직접 화면을 만들 수 있도록 몇 개 영역을 잠가 놨다(`permissions`, [README.md](../README.md) 의 "잠금 영역" 참고 — 에이전트에게 적용되는 규칙은 [CLAUDE.md](../CLAUDE.md) 에도 있다): [DESIGN.md](../DESIGN.md), [src/app/global.css](../src/app/global.css), [scripts/](../scripts/), [.claude/](../.claude/), [.husky/](../.husky/). 그런데 이 잠금은 기획자만 겨냥한 게 아니다 — **FE개발자와 디자이너도 똑같이 막힌다.** 제안층([DESIGN.proposed.yaml](../DESIGN.proposed.yaml))에 쌓인 토큰을 확정층으로 승격하거나, 브랜드가 확정돼 팔레트를 통째로 바꾸려는 사람이 Claude Code 에게 그 작업을 시키면 첫 시도에서 막히고, 이 문서를 찾기 전까지는 왜 막혔는지, 그럼 어떻게 해야 하는지 알 방법이 없다. 이 문서가 그 공백을 메운다.

## 왜 잠갔는가

이 다섯 영역은 검증 그 자체 — 게이트·훅·원장 — 를 정의한다. 에이전트가 정당한 코드 변경으로 게이트를 통과시키지 못하면, 그다음으로 값싼 수는 코드를 고치는 대신 **게이트 쪽을 손보는 것**이다. 스캐너 정규식을 느슨하게 하거나, 훅 커맨드를 지우거나, 원장 값을 코드에 맞춰 바꾸는 식이다. 이건 추측이 아니다 — 이 하네스를 만드는 과정에서 실제로 한 번 일어났다. 구현 에이전트가 게이트 오탐을 만나자, 코드를 고치는 대신 [src/app/global.css](../src/app/global.css) 의 주석에 있던 예시 문자열(`duration-200`)을 다른 표현으로 바꿔 새 스캐너를 피해 갔다. 리뷰에서 그 변경은 되돌려졌다 — 원장 파일은 검사가 불편하다고 고치는 대상이 아니기 때문이다. 잠금은 이 경로 자체를 막는다.

### `global.css` 는 이유가 다르다 — 풀기 전에 읽어라

`global.css` 잠금의 원래 근거는 두 Critical 우회로였다(설계 §4.2) — 비-hex `@theme` 색, 리셋 줄 삭제. **그 근거는 이제 소진됐다.** 게이트가 둘 다 잡고(F1·F2), 색·radius·그림자·서체·`.typo-*` 정의도 전부 잡으며, 제안층을 거치지 않은 `--color-*` 추가도 막는다. 그래서 "게이트가 다 잡는데 왜 잠갔나" 라는 판단으로 이 줄을 지우기 쉽다.

**지우지 마라. 게이트가 못 보는 것이 하나 남아 있다 — 뒤에 덧붙이는 CSS 다.** 실측(2026-09-03):

| 파일 끝에 추가한 것 | 게이트 |
| --- | --- |
| `.typo-body { font-size: 99px !important; }` | **통과** |
| `.card-x { padding: 13px; gap: 7px; }` | **통과** |
| `.typo-headline { color: … }` | **통과** |

`check_typography` 는 각 클래스의 **첫 번째** 정의만 읽는다. 그 아래에 같은 선택자를 다시 쓰면 CSS 캐스케이드에서는 나중 것이 이기는데 게이트는 앞의 것을 본다. 즉 **게이트가 방금 검증한 토큰을 그 다음 줄에서 무력화할 수 있고, 그것을 잡는 층이 없다.** 여백·크기 같은 비-색 속성은 애초에 검사 대상이 아니다(`scan_utilities` 는 Tailwind 클래스명 문법을 읽으므로 `.css` 를 건너뛴다).

이것은 `global.css` 외의 두 번째 `.css` 파일을 아예 금지한 이유와 같다 — "게이트가 검사하지 못하므로 존재 자체를 금지한다". `global.css` 는 그 규칙의 유일한 예외이고, 잠금이 그 자리를 대신 막고 있다.

풀려면 먼저 이 구멍을 막을 층을 만들어라. 후보는 `@theme` 블록만 별도 파일로 분리해 그 파일만 여는 것이다 — 열리는 표면이 토큰 선언으로 한정되고, 게이트가 이미 `@theme ⊆ 확정층 ∪ 제안층` 을 강제하므로 미등록 색은 여전히 막힌다.

## 정규 경로 — 에이전트를 거치지 않고 직접 편집한다

`permissions` 는 Claude Code 세션 안에서만 작동한다. 잠긴 파일이라도 에디터로 열어 직접 고치고 평소처럼 `git add`/`git commit`/`git push` 하면 된다 — 애초에 에이전트에게 "이 파일 좀 고쳐줘" 라고 시키는 것 자체가 성립하지 않는 요청이다. (참고로 세션 "안"에서는 이 `deny` 가 Edit/Write 툴 호출만이 아니라 `cp`·`echo > file`·`sed -i` 처럼 Bash 로 우회해 같은 파일에 쓰려는 시도도 실측으로 막는다 — 다만 그건 세션 밖, 즉 여기서 말하는 에디터 직접 편집 경로에는 애초에 적용되지 않는다.)

직접 고쳐도 검증이 사라지지는 않는다. `pre-commit`(`npm run lint && npm run check:tokens`)과 `pre-push`(`npm run verify`)는 husky 가 등록한 **git 훅**이지 Claude Code 권한이 아니다. 에디터로 고친 커밋도 이 두 훅은 똑같이 통과해야 한다. `--no-verify` 로 우회하지 않는다 — 게이트가 막으면 그 이유를 먼저 읽는다(`--no-verify` 는 [.claude/hooks/no-verify-guard.sh](../.claude/hooks/no-verify-guard.sh) 가 에이전트 쪽에서 막지만, 사람이 터미널에서 직접 치는 것까지는 막지 못한다).

### 잠금을 잠시 푸는 경우 — 주석 처리하지 말고 줄을 지워라

에이전트에게 잠긴 파일을 고치게 하려고 [.claude/settings.json](../.claude/settings.json) 의 `deny` 항목을 잠시 비활성화할 때가 있다. 이때 **`//` 로 주석 처리하면 안 된다.**

`settings.json` 은 엄격한 JSON 이라 `//` 가 들어가면 파일 전체의 파싱이 깨지고, 그러면 **주석 처리한 한 줄이 아니라 `permissions` 블록 전체가 조용히 사라진다.** 경고도 오류도 뜨지 않는다. `deny` 에 남아 있는 다른 아홉 줄까지 전부 무력화된 채로 작업하게 되고, 나중에 주석만 지우면 원래대로 돌아오니 그런 일이 있었다는 것조차 눈치채기 어렵다.

이건 추측이 아니라 실측이다. 이 하네스를 만들면서 `Edit(./.claude/**)` 한 줄을 주석 처리한 상태에서 `DESIGN.md` 와 `scripts/` 쓰기가 둘 다 통과했다 — 두 줄 모두 주석 처리되지 않은 채였다. 주석을 지워 유효한 JSON 으로 되돌리자 즉시 다시 막혔다.

**해당 줄을 통째로 지웠다가 끝나면 되돌려 넣는다.** 그리고 되돌린 뒤 `python3 -c "import json; json.load(open('.claude/settings.json'))"` 로 파싱을 확인한다 — 이 한 줄이 "잠갔다고 믿었는데 안 잠긴" 상태를 막아 준다.

**순서: 되돌리는 건 검증까지 전부 끝난 다음, 제일 마지막이다.** 고치자마자 되돌려 넣지 마라 — 되돌리는 순간 그 경로는 다시 잠기고, 세션 안에서는 다시 풀 수 없다(이 잠금 자체가 그러라고 있는 것이다). 이 순서를 지키지 않아 발생한 사고가 실제로 있다: 잠금을 풀어 `.claude/hooks/no-verify-guard.sh` 를 고친 뒤, 전체 검증을 끝내기도 전에 먼저 되돌려 놓았다가 스트레스 테스트 중 발견한 잔여 버그(브랜치명·경로에 든 하이픈 단어를 플래그로 오인하는 문제)를 고치지 못하고 남겼다 — 되돌리기 전에는 뻔히 고칠 수 있었던 문제였다. **다음 검증이 전부 끝나기 전에는 되돌리지 마라**: 전체 테스트 스위트, `npm run check:tokens`/`npm run verify`, 그리고 고친 부분을 직접(가능하면 훅을 직접 호출해) 스트레스 테스트한 결과까지.

### 훅을 고쳤으면 새 세션에서 확인하라

Claude Code 는 훅 설정(`.claude/settings.json` 의 `hooks` 블록, 그리고 각 훅 스크립트)을 세션 시작 시점에 한 번 읽어 그 세션 동안 그대로 쓴다. `.claude/settings.json` 이나 `.claude/hooks/*.sh` 를 고친 뒤 **같은 세션**에서 바로 테스트하면 여전히 고치기 전 동작이 보인다 — 위의 `//` 주석 경고와 같은 종류의 함정이다("고쳤다고 믿었는데 반영 안 됨"). 훅을 고쳤으면 새 세션을 열어야 실제로 반영된 훅을 확인할 수 있다.

## 제안층 승격 절차

토큰이 실사용으로 검증됐고 확정층에 편입할 만하다고 판단되면:

1. [DESIGN.proposed.yaml](../DESIGN.proposed.yaml) 에서 승격할 항목을 찾는다(`status: pending`).
2. [DESIGN.md](../DESIGN.md) frontmatter 의 `colors:` 블록에 같은 이름·값으로 옮겨 적는다. `origin`(`product` 또는 `derived`)과 `since`(YYYY-MM-DD)를 반드시 붙인다. 예:

   ```yaml
   info: { value: '#2D7FF9', origin: product, since: '2026-09-02' }
   ```

3. `DESIGN.proposed.yaml` 에서 그 항목을 지운다.
4. [src/app/global.css](../src/app/global.css) 의 `@theme` 에 `--color-info` 가 이미 있으면 손댈 필요가 없다. 없다면 지금 넣는다 — 게이트가 **붙여넣을 줄을 그대로 출력**하므로 `npm run check:tokens` 를 한 번 돌려 그 줄을 복사하면 된다.

   ```
   아직 @theme 에 없어 코드에서 쓸 수 없는 제안 1건: info
     src/app/global.css 의 @theme { ... } 블록 안에 아래 줄을 그대로 추가하세요:
         --color-info: #2D7FF9;
   ```

   **등록과 배선은 같은 시점이 아니어도 된다.** 제안층에만 있고 `@theme` 에 없는 색은 게이트가 위처럼 알리기만 하고 막지 않는다 — 등록은 에이전트가 하고 배선은 사람이 하므로 시차가 정상이기 때문이다. 다만 그 색을 **코드가 실제로 쓰면**(`bg-info`) 그때는 막는다. `@theme` 에 없는 색은 Tailwind 가 유틸리티를 만들지 않아 아무 스타일도 걸리지 않는 자리라서다.
5. `npm run check:tokens` 로 확인한다. 확정층 · 제안층 · `@theme` · 앱 코드 네 곳의 대조가 전부 통과해야 한다.

## 반려 절차

토큰을 확정층에 올리지 않기로 했으면:

1. [DESIGN.proposed.yaml](../DESIGN.proposed.yaml) 에서 해당 항목의 `status` 를 `rejected` 로 바꾼다. 필드 자체는 지우지 않는다 — 지우면 게이트가 "반려된 토큰"이라는 구체적인 메시지 대신 "원장에 없는 색"이라는 덜 유용한 메시지를 낸다.
2. 그 순간부터 `npm run check:tokens` 는 그 색을 여전히 쓰는 코드와, [src/app/global.css](../src/app/global.css) 의 `@theme` 에 남아 있는 `--color-<이름>` 선언 양쪽을 반려 사실을 명시한 메시지로 막는다.
3. 그 색을 쓰던 화면을 먼저 고치고(확정층에서 대안을 골라 교체), 그다음 `@theme` 에서 `--color-<이름>` 선언을 지운다. 순서를 반대로 하면(선언부터 지우면) 코드 쪽 사용처가 남아 있는 동안 잠깐 더 헷갈리는 메시지를 보게 된다 — 코드부터 고치는 편이 낫다.
4. 다시 `npm run check:tokens` 로 확인한다.

## 확정층 값 변경

`origin: brandbook` 값은 마브렉스 브랜드북이라 공통·고정이다 — 브랜드북 자체가 바뀔 때만 고친다. 프로젝트가 바꾸는 것은 `product`·`derived` 값이다. 출처는 `colors` 는 토큰마다, 나머지는 블록마다 달고, 블록 안에 출처가 섞이면 그 블록은 `product` 다.

[DESIGN.md](../DESIGN.md) frontmatter 의 `colors:` 값과 [src/app/global.css](../src/app/global.css) `@theme` 의 `--color-*` 값은 같은 원장의 두 표현이다. 게이트가 둘의 값 일치를 검사하므로 **양쪽을 같이 고쳐야 한다** — 한쪽만 고치면 다음 `npm run check:tokens` 에서 "값 드리프트"로 막힌다. `rounded`·`shadows.extruded` 같은 모양 토큰도 같은 원리로 두 곳에 동기화돼 있어야 한다.

## 플러그인 — 레포가 아는 것과 사람이 해야 하는 것

이 레포는 `frontend@marblex-plugins`(레이어드 아키텍처 규칙)를 쓴다. `.claude/settings.json` 에 두 가지가 적혀 있다.

| 키 | 하는 일 |
| --- | --- |
| `extraKnownMarketplaces` | 마켓플레이스가 **어디에 있는지** 알린다. 폴더를 신뢰하면 추가 프롬프트 없이 등록된다 |
| `enabledPlugins` | 그 플러그인을 **켠다** |

**둘이 있어도 설치는 자동으로 되지 않는다.** Claude Code v2.1.195 부터 외부 출처(git·GitHub·npm) 플러그인은 프로젝트 설정만으로 켜져 있어도 로드되지 않고, 사용자가 직접 설치해야 한다. 그때까지는 "설치되지 않음" 으로 보고하며 실행할 명령을 보여준다.

```bash
claude plugin install frontend@marblex-plugins
```

**설치하지 않으면 무엇이 달라지나** — 레이어 규칙의 *강제*는 `eslint.config.mjs` 가 레포 안에서 하므로 그대로 작동한다. 사라지는 것은 `frontend:architecture` 스킬의 *안내*다. 위반은 여전히 막히지만 에이전트가 배치를 판단할 근거가 하나 줄어든다.

**그리고 설치돼 있다고 스킬이 반드시 발동하는 것도 아니다.** 스킬은 모델이 상황을 보고 스스로 부르는 것이라 호출을 보장할 수 없다 — 이 레포에서 실제로 지시문이 발화하지 않은 사례를 측정한 적이 있다(템플릿 원본 레포의 `docs/superpowers/plans/2026-09-02-plan3-acceptance.md` — 프로젝트로는 복사되지 않는다). **보장은 게이트와 ESLint 가 지고, 스킬과 문서는 그 위의 안내층이다.** 이 구분을 흐리지 마라.
